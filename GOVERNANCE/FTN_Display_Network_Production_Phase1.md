# FTN Display Network — Production Phase 1

## Purpose
Turn Display Network from a basic interest form into a credible venue-deployment planning surface while preserving FTN ownership, vendor independence and honest infrastructure boundaries.

## Operational now
- Build a structured venue deployment brief.
- Capture venue type, country/territory, city/community, estimated screens, environment, connectivity, power/mounting readiness, screen purposes, audience context and deployment notes.
- Save deployment briefs locally through the shared FTN Integration Adapter.
- Carry FTN country context into the form.
- Review recent briefs on the same device.
- Route real commercial follow-up to FTN Commercial Partnerships.

## Not yet operational
- Managed device fleet.
- Screen CMS or remote playout.
- Advertising booking or billing.
- Proof-of-play reporting.
- Venue contracts or installation scheduling.
- Remote device management.
- Emergency alert authority.
- Cloud synchronization.

## Canonical future device record
When real deployments begin, FTN should own the normalized device/location record independently of hardware or CMS provider. Minimum fields should include FTN device ID, venue ID, authorized operator, territory, precise installation location, screen class, orientation, resolution, connectivity profile, power profile, operating window, content permissions, provider mapping, commissioning date, last health check, status and provenance.

## Product Mnemonic Layer
The Display Network mnemonic is the **Signal Mosaic**: multiple independent display surfaces connected into one network node. Ambiently it communicates physical digital infrastructure. After a successful deployment-brief save, each display activates in sequence and the network node radiates completion feedback. Reduced-motion settings disable animation.

## Ownership and provider independence
- Display Network must not make a signage vendor, CMS, hardware manufacturer or ad-tech platform the FTN system of record.
- Provider-specific identifiers remain mappings to FTN-owned canonical IDs.
- Credentials and device secrets never belong in public repositories.
- Future providers should connect behind shared FTN interfaces and be replaceable.
- Capability metadata should distinguish FTN-native, FTN-hosted, connected-provider and external-provider capabilities only when those distinctions become operationally useful.

## Future orchestration seam
The deferred **FTN Autonomous Opportunity & Provider Engine** may eventually evaluate display hardware, CMS, connectivity, maintenance and advertising providers. No provider registry, router or autonomous purchasing logic is introduced in this phase.

## Merge gate
Desktop/mobile visual review, interaction testing, storage behavior and form accessibility remain required before merge.
